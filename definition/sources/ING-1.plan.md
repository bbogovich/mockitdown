# ING-1 plan: the design-tool web components for the MockItDown Designer

Prompt (verbatim): "next the editor web compoentns to support the MockItDown-Designer needs to be created."

## Scope and conventions

- This plan builds SRC-12#s17 milestones 1-6 in this repository (`typescript/`, tag prefix `mockitdown-`):
  the editing core, the design session and events, the editor, outline, gallery, inspector, code view,
  diagnostics list, canvas and designer composite, and the designer test page `typescript/pages/designer.html`
  (SRC-12#s12). Milestone 7, the Electron shell, belongs to the designer project (SRC-16 S1-S8).
- Anchors: SRC-12 is cited by numbered section (`SRC-12#s6.3`); the mockups SRC-13..15 by callout
  (`SRC-13#p1.c4` = SRC-13, callout 4).
- Constraints: no runtime dependencies (R-WEB-001.C1, ADR-20); web components and CSS, no framework; the code
  view is built in-house with no editor library (SRC-12#s9, SRC-12#s14 "Dependencies"); the Python variant
  stays the reference for the language (ADR-18).
- State verified 2026-11-26 against this repository. SRC-16's "current state" paragraph (mockitdown 0.1.0,
  milestone 0 only) is stale. Today the repository has:
  - the TypeScript core (lexer, parser, evaluator, renderer port; all 572 conformance cases byte-identical);
  - `mockitdown-mockup` (R-WEB-002), the dev server on `node:http` (R-WEB-003), the Playwright harness
    (R-WEB-005) and the pack gallery `pages/packs.html` with Elements and Examples tabs (R-WEB-004);
  - `shared/reference/<pack>.json`, generated by `python/tools/gen_reference.py`, giving every element its
    name, role, params, defaults, variants, doc, `own`, `sample` and `variants_sample`;
  - 38 packs, 3132 element definitions over 89 roles.
- What the editing core still lacks (SRC-12#s13 against the code):
  - **W1.1 (syntax tree).** Not done. `Location` holds `line`, `col` and `source` only: no offsets, no end
    position, no node ids (`typescript/src/core/diagnostics.ts`, `core/syntax/ast.ts`). The lexer drops
    comments.
  - **W1.4 (edit-mode render).** Not done. The renderer emits `data-el="<name>"`, not a node id
    (`core/render/html.ts`). `M-VIEW-1` carries `loc` only.
  - **W1.5 (role rule table).** Not done. `shared/language/` holds only `vocabulary.json`. Elements have a
    `role`, but no role has a category, accepted children or an attachment mode.
  - **W1.6 (typed parameters).** Not done. `params` lists names only (M-PACK-2.F3). Pack `modifiers` map a name
    to an `attr`. `vocabulary.json` lists rendered and ignored modifier names, without types.
  - **W1.7 (element samples).** Done as data: all 134 base elements and every pack element have a `sample`
    in `shared/reference/<pack>.json`. One gap remains: `scripts/copy-shared.mjs` does not copy
    `reference/` into `dist/shared/`, and R-REPO-002.C5 forbids reading `shared/` at run time. A gallery
    component shipped in the package cannot reach the samples, so they must be published (S3).
  - **W1.8 (HANDOFF backlog).** All three items are open in `HANDOFF.md`: unknown labelled arguments are
    dropped silently, dotted element names do not parse, and overlay layers drop their callouts.
- The project has no design tier (`.specitout/sdd.json` tiers: definition, specification, implementation).
  Question Q6 asks how the editor screens are recorded.

## Questions for the developer

1. **Which code owns `.mkdesign`?** (SRC-16 Q1; SRC-12#s11, SRC-12#s17.) Blocks E5 and the designer's D5.
   Options:
   - (a) the designer shell's core module, with mockitdown taking plain objects;
   - (b) the shell for now, replaced by mockitdown in S6;
   - (c) a small pure module in mockitdown, built early in S2 (E5) and exported as a package subpath
     (for example `mockitdown/design`), used by the composite and the shell alike.

   **Recommended: (c).** `open(json)` and `toJSON()` need the schema in S2 anyway. One implementation avoids two
   validators drifting apart, and the module works in Node for the shell's main process. A sub-question for (c):
   should the module also hold the Markdown and folder import and export (SRC-12#s11 "Export"), or do these stay
   in the shell (SRC-16 D6, D18-D21)? Recommended: they stay in the shell for now.
2. **Pack per mockup or per document?** (SRC-12#s18 Q4.) Affects the E5 schema and the gallery (E10). Options:
   - (a) per mockup, with `defaults.pack` for the document, as in the SRC-12#s11 example;
   - (b) one pack per document;
   - (c) per mockup, with the Mockups list flagging mockups whose pack differs from the default.

   **Recommended: (a)**. It is what the schema already shows and keeps comparisons possible. (c) can be added
   later without a format change.
3. **How deep should the code editor go?** (SRC-12#s18 Q2.) An editor library is already excluded by your
   constraint, so this is only about scope. Affects E19. Options:
   - (a) the light editor of SRC-12#s9: colouring, line numbers, diagnostics, bracket matching, auto-indent;
   - (b) (a) plus in-house find and replace;
   - (c) (b) plus folding.

   **Recommended: (a) now**, with find and replace as a later issue if needed. Multi-cursor is not planned.
4. **Should Python get the edit API?** (SRC-12#s18 Q5; SRC-12#s13 wants "the same printing rules … checked by
   conformance cases"; SRC-12#s16 says "Python runs the same cases once it implements" it.) Affects E1-E3.
   Options:
   - (a) TypeScript only, with the edit corpus kept as language-neutral data in `shared/conformance/edit/` so
     Python can adopt it later, and the choice recorded as an ADR;
   - (b) Python in the same issues, which roughly doubles S1.

   **Recommended: (a).** SRC-12 makes the Python edit API conditional, and no current tool needs structural edits
   from the command line.
5. **Does the edit-mode render option need a Python counterpart?** Affects E4. ADR-18.C1 says every rendering
   change is made in both variants, in the same issue, with a conformance case. R-REPO-004.C3 says the expected
   HTML is produced by Python. Options:
   - (a) both variants: the option emits deterministic per-parse node ordinals (`data-mkd-node="n12"`), the
     conformance corpus gains edit-mode cases, and the TypeScript session maps ordinals to its stable ids;
   - (b) TypeScript only, with an ADR that exempts the editing-only attributes from ADR-18 and node:test cases
     outside the conformance corpus.

   **Recommended: (a).** The cost is small (both renderers open elements through one tag builder), and it keeps
   one rendering truth and gives Python tools source mapping for free.
6. **Where are the editor screens recorded?** The project has no design tier, but SRC-13..15 are screen mockups
   with callouts. This decides whether vibe-plan's define step writes design items. Options:
   - (a) add a design tier (`design/` with SCR-EDT items for Design mode, inserting and the canvas, from
     SRC-13..15) before S2;
   - (b) no design tier: the specification's requirements for the components cite F-19, F-20 and the sources
     directly, and SRC-13..15 stay as illustrations.

   **Recommended: (b)** for this library prototype. The designer project's own SCR-APP-01 is where the screen
   lives (see SRC-16 Q13).
7. **Typed parameter metadata at role level?** Affects E13. Options:
   - (a) types per role parameter in `roles.json`, with per-element overrides in `pack.json`;
   - (b) types on every element's `params` in `pack.json`, changing M-PACK-2.F3 from names to objects.

   **Recommended: (a).** It avoids editing 3132 element definitions and keeps `params` backward compatible.
8. **Should the remaining HANDOFF defects be planned now?** SRC-12#s13 lists dotted element names and overlay
   callouts beside the unknown-argument warning (which S4 plans as E14). Options:
   - (a) plan them as S7 (E26, E27), independent and low or medium priority;
   - (b) leave them in HANDOFF.

   **Recommended: (a).**
9. **Should Python warn on misplaced roles?** (SRC-12#s13: "The Python checker can use it too.") Options:
   - (a) not now: `roles.json` is published in both packages, but only TypeScript enforces it;
   - (b) a Python warning in E9, which changes `diag.json` for any existing source that breaks a rule.

   **Recommended: (a)**, with a follow-up once the rules have been exercised by the gallery.
