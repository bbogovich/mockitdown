1. Purpose and scope

mockitdown mockups are written as code: a SwiftUI-style notation rendered in the style of one of 38 UI framework packs. That suits developers but not UX designers. The MockItDown Designer lets a designer build the same mockups in a familiar visual editor: drag elements from a gallery, arrange them in an outline, set their properties in an inspector, and lay several screens out on a zoomable canvas. The output is ordinary mockitdown code, so the same mockup renders unchanged in a Markdown site, in a <mockitdown-mockup> element, and in SpecItOut design and specification projects.

The designer is a demo and test application. Nearly all of its behaviour lives in reusable web components in the mockitdown repository (typescript/, tag prefix mockitdown-). Any web application can host those components. The Electron application adds only what a desktop editor needs: files, menus, windows, autosave and packaging.

In scopeOut of scope
  • The gallery, outline, inspector, editable view, code view and canvas components
  • Insertion by drag-and-drop or by an Add button, limited to the elements allowed at that point
  • Outline-first selection, with click-to-locate in the view
  • Several named mockups on an infinite canvas
  • Saving a design document, and exporting it to Markdown and HTML
  • Undo and redo, and two-way editing between the visual view and the code
  • AI generation or a prompt view (the MockItOut Designer's Claude terminal is not carried over)
  • Real-time multi-user collaboration and cloud storage
  • Free-form vector drawing, with pixel positions outside layout containers
  • Interaction prototyping: links between mockups and click-through flows (see §18)
  • Authoring packs (packs stay JSON and CSS files, edited by hand)

The interaction model follows Axure rather than Figma. Axure keeps the element hierarchy in view at all times, and inserting, removing or re-parenting elements is the main editing activity. Figma's pointer-first, free-position model breaks down when every element sits in a layout container.

3. Where the designer sits

Figure 1. The application is a thin shell. Editing logic lives in the mockitdown components, so other web applications get the same editor.

The designer depends on a released version of the mockitdown NPM package. While both are in development it uses a local path. Any change to editing behaviour goes into the mockitdown repository, through its VibeItOut queue, with browser tests on the component test page (F-19.C10). The Electron application has its own tests for its shell only.

5. Selecting elements

Nested elements make a click ambiguous: a click on a button's label could mean the label, the button, the stack around it, or the card around that. The outline is therefore the primary means of selection, and a click in the view is a fast way to locate an element in the outline.

  • Click in the view selects the innermost element under the pointer. Its outline row is revealed, with its ancestors expanded and the row scrolled into view, and the element is outlined in the view (F-19.AC3).
  • Click again on the same spot, or press Esc, to move the selection to the parent. Enter moves back down to the previously selected child. Alt-click cycles through every element stacked under the pointer.
  • Hover in the outline or the view draws a thin outline on the element in the other, with its name and size as a tag.
  • The breadcrumb in the status bar shows the path from the root and selects any ancestor in one click.
  • Keyboard in the outline: arrows move and expand or collapse, Home and End jump, and typing finds the next matching row.
  • Multi-select (Shift for a range and Cmd/Ctrl for single rows, among siblings only) for delete, duplicate, wrap and move.

Outline rows reuse the MockItOut row anatomy: the element name, then its main label (the first argument, as in Button "Sign in"), then an #id chip when the element has an identifier. Rows of derived elements, which come from ForEach, if or a custom component, are drawn in italics with a link icon. Selecting one selects its source construct (see §9).

6. Inserting elements

{{mockup:insert|--pack sketch --device fit --title "Inserting into the selected HStack"}}
Figure 3. With HStack #actions selected, the gallery offers only the elements allowed inside a horizontal stack (2) and says how many it hides and why (3). Dragging Toggle onto the outline shows where it will land (1).

The gallery

  • The gallery lists the elements of the active mockup's pack: the pack's own elements first, then the inherited core vocabulary. They are grouped by role category (§6.3) and drawn as small live previews rendered in the pack's style, the same samples the Reference pages and the pack gallery test page use.
  • A search field filters by name, role and doc text. A Components group lists the custom components (structs) the mockup imports or declares.
  • With no selection the gallery shows everything allowed at the root of a mockup. With a selection it shows only what may be a child of the selected element. A footer group, Hidden here, names what is filtered out and why, so the rule is never a mystery.

Three ways to insert

  1. Add button (or double-click, or Enter on a focused gallery item): inserts the element as the last child of the selection, then selects it (F-19.C3, AC2).
  2. Drag onto the outline: a drop indicator shows before, after or inside the row under the pointer. Positions that break the rules show a "no entry" cursor and a short reason.
  3. Drag onto the view: the innermost container under the pointer is outlined, and an insertion bar shows the position along its axis (vertical for a VStack, horizontal for an HStack). The rules are the same.

A newly inserted element gets its sample's arguments (for example Button("Button")). Its first text field opens for editing right away, so naming it takes one keystroke sequence.

6.3 Containment rules

Which elements may go where is decided by role, from a rule table that both the components and any future validator read (§13). The categories, with examples from the core vocabulary:

CategoryRoles (examples)May contain / may be placed in
FrameNavigationStack, NavigationSplitView, TabViewOnly at the root of a mockup, as a split-view column or as a tab's content. Never inside a stack, card or list
BarAppBar, Toolbar, SidebarInside a frame or the root stack. A toolbar accepts only toolbar items, buttons, pickers and search fields
LayoutVStack, HStack, ZStack, Group, ScrollView, Grid, Form, Section, CardContain any layout, content or control element. A Grid accepts only GridRow
CollectionList, Table, Tree, Timeline, Board, Menu, Tabs, StepsOnly their item roles: List → Row/ListItem/Section; Table → TableColumn/TableRow; Tree → TreeItem; Menu → MenuItem; Board → BoardColumn → KanbanCard
Content and controlText, Image, Icon, Badge, Button, Toggle, TextField, Picker, Slider, Chart …Leaves: they have no children, except a Button or Link with a custom label
OverlayDialog, Sheet, Alert, Toast, Tooltip, MenuAttached to an element through a presentation modifier (.sheet, .alert, .overlay), not placed as a child. The gallery offers them as Attach … actions on the selection
AnnotationCallout, Pointer, SelectionRect, highlightAttached as modifiers to any element. Offered in the inspector's Annotations group

A pack element inherits the rules of its role, so VBtn behaves as a Button and ShellBar as a Bar. A pack can tighten the rules for one element in pack.json (for example, a Fiori ObjectPageLayout that only accepts sections).

The inspector shows the selected element in four groups. The controls are generated from pack data, so a new pack needs no inspector code.

Edits apply as you type, debounced to 150 ms, and one burst of typing forms one undo step. 9. Code view and round-trip

The code is the source of truth. Every visual edit is an edit to the code: an insertion, removal or replacement of a text span. The editor never regenerates the whole mockup from a model. This keeps the author's formatting, comments, let bindings, ForEach loops and if conditions intact, and keeps diffs small.

  • The core parses the code into a syntax tree that keeps source positions and whitespace. Each element call in the tree has a stable node id while its text survives an edit.
  • When editing, the renderer tags every element it emits with the node id it came from (§13). This is how a click in the view finds its outline row.
  • Derived elements come from a ForEach body, an if branch or a custom component's body, so one source node draws many view elements. In the view they select their source node and show a "derived" badge. The inspector edits the source (so changing the loop body changes every row) and offers Edit in code for anything it cannot express.
  • Editing in the code view re-parses after a 300 ms pause. If the code is valid, the outline and view update and the selection is kept by node id. If not, diagnostics appear in the gutter and the status bar, and the visual panels keep showing the last valid tree, read-only, until the code parses again (F-19.AC5).
  • The code view is a light editor built for this project: a text area with syntax colouring, line numbers, diagnostics, bracket matching and auto-indent. It adds no third-party editor dependency. Whether that is enough is an open question (§18).

10. The infinite canvas and named mockups

{{mockup:canvas|--pack sketch --device desktop --width 1100 --height 420 --chrome macos --title "Canvas — three named mockups"}}
Figure 4. A canvas holding three named mockups (1, 2). The active mockup, Inbox, is highlighted and is the one the outline, gallery and inspector act on. A minimap (3) shows the whole canvas.
  • Zoom from 10 % to 400 % with Cmd/Ctrl + scroll, pinch, the toolbar control or Cmd/Ctrl + plus/minus. Cmd/Ctrl + 0 fits all mockups; Cmd/Ctrl + 1 sets 100 %; Shift + 2 fits the selection. Mockups stay sharp at every zoom level because they are HTML, scaled with CSS transforms and laid out again past 200 % (F-20.AC1).
  • Pan with scroll, by dragging with the space bar held, by middle-dragging, or by dragging the minimap viewport.
  • Mockups as frames. Each mockup is a frame with a name label above it. Drag the label to move the mockup. Double-click the label to rename. New mockups are placed in the first free slot to the right, and a frame can snap to an 8 px grid and to its neighbours' edges.
  • Names are unique within a document, are case-sensitive and may contain spaces. Renaming to a taken name is refused with a message (F-20.AC2). A name is the key that SpecItOut tools import by, so the Mockups list warns when a name is still a default such as "Mockup 3".
  • Activating a mockup. Clicking a mockup's frame, or choosing it in the Mockups list, makes it active. Inactive mockups render like Preview mode, which keeps large canvases fast (F-20.AC4).
  • Sections (optional). A named rectangle behind a group of mockups, for example "Onboarding flow". It becomes a heading in Markdown export.

11. The design document file

A design document is one JSON file, *.mkdesign. It is readable, diffable and stable in key order, and each mockup's code is kept verbatim, so it can be read without the designer.

{
  "format": "mockitdown-design",
  "version": 1,
  "name": "Mail app",
  "defaults": { "pack": "fluent", "appearance": "light" },
  "imports": ["components/cards.mockitdown"],
  "sections": [ { "name": "Onboarding", "x": -40, "y": -60, "w": 1400, "h": 900 } ],
  "mockups": [
    {
      "name": "Sign in",
      "x": 0, "y": 0,
      "options": { "pack": "fluent", "device": "desktop", "width": 480, "height": 360, "title": "Sign in" },
      "code": "NavigationStack {\n  VStack(spacing: 12) {\n    Text(\"Welcome back\").font(.title2)\n    …\n  }\n}\n"
    }
  ],
  "view": { "zoom": 0.75, "x": 120, "y": 40, "active": "Sign in" }
}

Export

  • Markdown: one ```mockitdown fence per mockup, in canvas order (top-to-bottom, then left-to-right, within sections). The mockup's name goes in the fence's id and title attributes, with a heading per section. The result drops straight into a Zensical or MkDocs site.
  • Folder of files: one <name>.mockitdown per mockup, plus index.json with the names, positions and options. SpecItOut's Design-project skills instead read the .mkdesign file and pick mockups by name into requirements (§18).
  • HTML: a standalone page with every mockup rendered by <mockitdown-mockup>. PNG: the active mockup or a selection of them, at 1×, 2× or 3×.

Opening a .mockitdown file creates a one-mockup document named after the file. Opening a Markdown file imports each mockitdown fence as a mockup and offers to save the result as .mkdesign.

12. Web components

All components are standard custom elements written in TypeScript with no framework (no React; see §15). Each renders into a shadow root and is styled through CSS custom properties and ::part. They share one design session, a plain object holding the document, the active mockup, the selection and the undo history. A component joins a session either by being placed inside a <mockitdown-designer> or through a session property set by the host.

Events, which bubble and cross the shadow boundary: mockitdown-select, mockitdown-change (with the text edits made), mockitdown-insert, mockitdown-rename, mockitdown-diagnostics. A host application such as the Electron shell listens for mockitdown-change to mark the document dirty and schedule an autosave.

The mockitdown repository gains a designer test page (typescript/pages/designer.html) that composes these components with a sample document. It is used for demos and Playwright tests (F-19.C10), and is the same page the Electron app loads, with file access added.

13. Requirements on the mockitdown core

The visual editor needs a few things from the shared core that rendering alone does not. Each will be specified in the mockitdown repository before the design-tool issues are queued.

  1. A syntax tree that keeps positions and formatting, with stable node ids, and an edit API: insert, remove, move, set argument, set modifier, rename. Each operation returns minimal text edits plus the new tree. Python and TypeScript share the same printing rules for new code (indentation, argument order), checked by conformance cases.
  2. Source mapping in the rendered HTML: an edit-mode render option that adds data-mkd-node="<id>" to every element produced from a call, and marks derived elements.
  3. A shared role rule table, shared/language/roles.json, holding each role's category, accepted child roles and attachment mode (child, modifier or presentation), with per-element overrides in pack.json. The Python checker can use it too, to warn about an AppBar inside an HStack.
  4. Typed parameter metadata in pack.json and the modifier vocabulary (text, number, Boolean, enum, colour, icon, array), so the inspector can choose its controls. Today an element declares only names and defaults.
  5. Element samples as data, already planned for the pack gallery test page: shared/reference/<pack>.json.
The core backlog already noted in mockitdown's HANDOFF has items that affect editing directly: unknown labelled arguments are dropped without a warning, dotted element names do not parse, and overlay layers lose their callouts. The editor should not hide these. The inspector will show unknown arguments as "not understood by this pack".

Behaviour

  • Documents and windows: one window per design document; the window title shows the document name and an "edited" marker; the window's size and position are restored; a recent-documents list is kept; double-clicking .mkdesign opens it, which needs a file association.
  • Menus: File (New, Open, Open Recent, Save, Save As, Export ▸ Markdown · Folder · HTML · PNG, Close), Edit (Undo, Redo, Cut, Copy, Paste, Duplicate, Delete, Select Parent), Insert (by category, mirroring the gallery), Arrange (Wrap, Unwrap, Move Up/Down, Convert, Extract Component), View (Design/Preview/Code, Zoom, Panels, Appearance), Mockup (New, Rename, Duplicate, Delete, Pack, Device), Help.
  • Autosave and recovery: changes are written every 30 seconds to a recovery file beside the application data, never over the document. After a crash the recovery is offered on the next launch.
  • Security: contextIsolation: true, sandbox: true, nodeIntegration: false, a strict Content-Security-Policy with no remote content, and the preload exposes only the named file operations. Mockups that reference remote images show placeholders unless the user allows remote images for that document.
  • Packaging: electron-builder for macOS (signed and notarised), Windows and Linux. The MockItOut prototype's Electron build was removed by macOS XProtect at launch because Apple had explicitly blocked the older Electron version it used. This app tracks the latest stable Electron release, which avoids that block.

16. Testing

  • Component tests (mockitdown repository): Playwright against pages/designer.html, one test or more for each acceptance criterion of F-19 and F-20, run in the same npm test as the renderer tests.
  • Core tests: node:test for the edit API. Each operation is applied to conformance sources and the resulting text is compared with expected files. Python runs the same cases once it implements the same edit API.
  • Application tests (this repository): Playwright's Electron launcher drives the real app. Tests cover New → insert → save → reopen, autosave recovery, export to Markdown followed by building it with the Python mockitdown in strict mode, opening Markdown with three fences, and menu shortcuts.
  • Manual review script: a checklist in the README that walks through Figure 2's flow in each mode, at three zoom levels, in light and dark appearance.

18. Open questions

  1. SpecItOut import shape settled. The importer is defined as part of SpecItOut's new Design project type, and is managed from the rewritten SpecItOut app. Skills select specific mockups by name from a designer file and import them into individual requirements. One requirement often holds several mockups that together illustrate a workflow, so names must stay stable, and the order of a selection is significant.
  2. Code editor depth. Is the built-in light editor enough, or is a full editor library such as CodeMirror 6 (MIT, modular, about 150 kB) worth a dependency for search, multi-cursor and folding?
  3. Flows. Should a later version link mockups (a button in "Sign in" leads to "Inbox") and export the links for SpecItOut flow design objects?
  4. Pack per mockup or per document. This design allows a pack per mockup, with a document default. Is mixing packs on one canvas, for example to compare Fluent and Material, a wanted use or a source of mistakes?
  5. Python edit API. Should the Python variant implement the same edit API (milestone 1) so command-line tools can make structural edits, or should editing stay TypeScript-only?
