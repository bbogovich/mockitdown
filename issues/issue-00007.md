## Prompt (verbatim, SRC-8; local paths redacted)

> We need to support a TypeScript implementation that defines web compoents to render mockitdown designs in a web app.  This was going to be a separate project, but since they would share the same CSS to support the packs it makes more sense to implement both the Python and JavaScript versions in the same project so that the language and content packs are consistent as a shared resource between the two.
>
> Restructure the project to support the two variants.  The existing python library code can be consolidated in a "python" folder, and the web components in a "typescript" folder.  Common assets used by both can be in a "shared" folder, including the stylesheets, any images, and other objects that both implementations would publish.
>
> The web compoents for the TypeScript variant will include components for both rendering and editing mockups in a web app.  The web component prefix will be "mockitdown-" for easy identification.  The TypeScript project will include test pages for both demo and test automation purposes to verify that the components render correctly and are interactive.
>
> The first component is a renderer to embed a mockup in HTML.  This will be "mockitdown-mockup".  The mockup's code block (same as in markdown) will be the only child node, represented as a CDATA block.  The syntax for the mockup itself is identical to the markdown version, it is a shared language and supports the same import mechanisms to load content packs to render different UI frameworks.
>
> A renderer test page is required to evaluate all packs and their mockup elements.  The app is a "master-detail" style layout, with a left panel allowing selection of pack, and main content area including renderers to illustrate each UI element type plus full examples of common app design patterns that would use the components.
>
> The resulting TypeScript library will build as a packaged NPM module, so it is a NodeJS project, but with no backend and should have the minimum set of dependencies needed for a test harness and to serve the test pages for user manual review.  The built in Node HTTP library can be used to serve the pages; including Express or another full web server for this is unnecessary.
>
> The other category of web compoents are design tools.  UX designers are generally not comfortable with creating mockups as code, so tools to support creating mockups in a familiar style user interface is necessary.  Figma is the current most popular web hosted app for this, although the Axure desktop app may be a better model for this case since the component hierarchies need to be easily navigable to insert, remove, or edit the design elements.
>
> The design tools need to include support for selecting the possible elements that compose a mockup from a gallery and inserting them into the design either through drag-and-drop or if an element is currently selected an explicit add button press to insert the element as a child.  If an element is already set active, the gallery is filtered to the set of elements that are applicable.  When a horizontal box within an app design is active, for example, adding an app frame inside of it makes no sense so the user shouldn't be able to insert it.  Elements should be selectable on click, ideally, but since nested elements make it ambiguous what a user intended to select an outline view would be the primary means of component selection, with clicking on an element narrowing the user's search by autoselecting the item in the outline and highlighting it in the view.
>
> Multiple mockups may be created in a single page, so an "infinite canvas" view that a user can zoom and pan around is needed for some applications.  Each mockup within the webapp is assigned a name so that tools creating design and specification projects (see specitout2) can import them into the appropriate locations.
>
> Restructure the repository to be home for both the python and typescript implementation.  Create an initial test page for the TypeScript version as described hosting read-only representations of all packs and their component elements as mockitdown-mockup web components.  Produce a design document PDF for a demo designer to include as a test app supporting the described features and any other meaningful functionality needed for creating and editing the mockups.  A nice presentation for outline view and element property display already exists in the MockItOut Designer prototype (clone of Figma Make)  at [local path]/MockItOut/prototype/MockItOut which can be partially reused.  That is an AI-driven app, which is functinality we won't be including here.  The standard designer app prototype will be an electron app in [local path]/MockItDown-Designer-Prototype.
>
> Reminder this is a VibeItOut project and should have the plugin from SpecItOut2 installed.

Clarifications: CDATA replaced by a `<script type="text/mockitdown">` child (ADR-19); dev dependencies typescript + @playwright/test only (ADR-20); design tools defined now, built after the designer design document is reviewed.
