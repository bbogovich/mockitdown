# Decisions: web variant and design tools

The decisions behind the editing core and the design-tool components: which variant offers the edit
API, and how a rendering made for editing stays one rendering truth across both variants.

#### ADR-21 — The edit API is TypeScript-only, with a language-neutral edit corpus

**Context.** SRC-12#s13 wants the same printing rules in both variants, checked by conformance cases,
and SRC-12#s16 says Python runs the same cases "once it implements" the edit API. ADR-18 makes the Python
variant the reference for everything both variants do.

**Decision.** Only TypeScript edits code structurally, for now. The rules it follows are kept as
language-neutral cases (source, operation, expected text), so they are specified once and a Python
implementation can adopt them unchanged.

**Consequences.** The editing core is built in one language; nothing in the Python variant changes for
it, except the edit-mode rendering, which is a rendering change (ADR-22).

Re-checked at 0.10.3 together with the items it cites or is cited by (specification audit, #51): the citations are still accurate and no obligation changed.

**Re-checked at specification 0.10.7.** Its prerequisites were re-checked after the renderer split (#48, #49) and the gallery spec split (#50) without any change to an obligation; neither is this item changed.

**Re-checked at 0.11.0.** Its cited items R-EDIT-001, R-EDIT-002, R-EDIT-003 changed with SRC-18 (all packs recorded, stylesheet partials, gallery home page and easter eggs, TypeScript release builds, new packs); no obligation of this item changed.

**Constrains.** R-EDIT-001, R-EDIT-002, R-EDIT-003

| | Statement |
|---|---|
| D1 | The syntax tree with node identities and the structural edit API (R-EDIT-001, R-EDIT-002, R-EDIT-003) are built in the TypeScript variant only. |
| D2 | The printing rules for new code are fixed by the edit corpus `shared/conformance/edit/`, data without code, which a later Python edit API MUST pass unchanged. |
| O1 | rejected: the edit API in Python in the same issues — it roughly doubles the editing core's first stage, and no current tool needs structural edits from the command line (SRC-12#s18). |
| O2 | rejected: printing rules in prose only — two implementations would drift; cases decide what "the same rules" means. |
| C1 | The edit corpus's expected files are written and reviewed by hand; they are not generated by the Python renderer, so ADR-18.D2 does not govern them. |
| C2 | A Python edit API, if one is wanted, is a new requirement that cites the corpus and this decision. |

#### ADR-22 — The edit-mode rendering exists in both variants, with per-parse node ordinals

**Context.** ADR-18.C1 says every rendering change is made in both variants with a conformance case,
and R-REPO-004.C3 says the Python renderer produces the expected HTML. The design tools need each rendered
element to name the call it came from.

**Decision.** Both renderers gain the option. What they write is a node's ordinal — its position among
the view nodes of the source — which both parsers compute identically; the session turns an ordinal into
its stable id after each parse (R-EDIT-006.C9).

**Consequences.** The cost is small (both renderers open role elements through one tag builder), there is
one rendering truth, and the corpus grows by a handful of edit-mode cases.

Re-checked at 0.10.3 together with the items it cites or is cited by (specification audit, #51): the citations are still accurate and no obligation changed.

**Re-checked at specification 0.10.7.** Its prerequisites were re-checked after the renderer split (#48, #49) and the gallery spec split (#50) without any change to an obligation; neither is this item changed.

**Re-checked at 0.11.0.** Its cited items R-EDIT-004, R-REPO-004 changed with SRC-18 (all packs recorded, stylesheet partials, gallery home page and easter eggs, TypeScript release builds, new packs); no obligation of this item changed.

**Constrains.** R-EDIT-004, R-REPO-004

| | Statement |
|---|---|
| D1 | The `edit` render option (R-EDIT-004) is built in both variants, in the same issue, with conformance cases, as ADR-18.C1 requires of every rendering change. |
| D2 | The rendered attributes carry node ordinals (`data-mkd-node="n12"`), which each parser computes from source positions alone; the TypeScript session maps ordinals to its stable node ids. |
| O1 | rejected: the option in TypeScript only, with an exemption from ADR-18 for editing attributes — two rendering truths, and edit-mode output outside the conformance corpus. |
| O2 | rejected: stable node ids in the HTML — they depend on the history of edits, which only the editing session has, so the Python renderer could not produce them. |
| C1 | The edit-mode cases' expected HTML is generated by the Python renderer like every other case (R-REPO-004.C3). |
| C2 | Python tools gain source mapping of rendered elements without an edit API. |

#### ADR-23 — TypeScript releases under their own tags, as GitHub release assets

**Context.** SRC-18#gallery asks for release builds of the packaged TypeScript library on GitHub. The
repository already releases the Python package by tags `vX.Y.Z` that `.github/workflows/release.yml` checks
against `python/pyproject.toml` and publishes to PyPI.

**Decision.** The TypeScript package keeps its own version line and its own tag prefix, `ts-v`, and is
released by its own workflow as an archive on a GitHub release.

**Consequences.** Two independent release flows that cannot trigger each other; the gallery home page and
the TypeScript README point at the releases page; moving to the npm registry later is one more step in
the same workflow.

**Constrains.** R-WEB-007

| | Statement |
|---|---|
| D1 | The TypeScript package is released under its own tags `ts-vX.Y.Z`, with its own version line in `typescript/package.json`, by its own workflow, separate from the Python package's `vX.Y.Z` tags and PyPI workflow. |
| D2 | A TypeScript release is published as the `npm pack` archive attached to a GitHub release; it is not published to the npm registry. |
| O1 | rejected: one tag and one GitHub release for both variants — the Python package is at 0.4.0 and the TypeScript package at 0.1.0, the Python workflow requires the tag to equal its own version, and a shared tag would force the two version lines into lockstep and tie a PyPI failure to the TypeScript release. |
| O2 | rejected: publishing to the npm registry now — it adds an account, a token or trusted-publisher setup and a public name to maintain, while the request asks only for release builds on GitHub; it can follow without changing D1. |
| C1 | A TypeScript release needs a version bump in `typescript/package.json` and a `ts-v` tag; it never moves or reuses a pushed tag, and a failed release after the GitHub release exists is followed by the next patch version. |
| C2 | Projects install a release by the archive's URL (`npm install <url>`), which pins the exact build. |
